# Agent Note: 整理地址补全与原文回退提示

Status: implemented

## Problem

模型列表支持 API 前缀，macOS 原生整理却把同一个前缀直接作为 POST 地址。一次获准的合成探测在前缀地址收到 HTTP 301；请求未到模型，不能据此归因于 thinking 或 30 秒预算。既有异常处理返回原始转写而无提示，用户无法分辨整理成功和失败回退。

## Decision

Shurufa 的 `HTTPVoiceRequest` 使用 URL 组件处理对话地址：校验原地址后，为主机根路径、末段为 `v` 加 ASCII 数字的版本前缀，以及兼容接口 `/v1beta/openai` 补 `/chat/completions`。完整标准对话地址仅去掉末尾斜杠，查询参数保留。其他自定义完整路由逐字保留，包括尾斜杠。非 Shurufa 的地址维持原有原样 POST，不依赖重定向。该入口仍调用共享 `polish_cloud_text`，厂商判断、thinking 规则和 30 秒总预算保持不变，不猜测自建端点背后的模型。

整理结果增加只读 `polishFailed` 状态，在主队列完成回调前写入；失败返回完整原始转写，取消不交付。HTTP、系统语音与 TextStream/流式服务的最终投递均传递该状态。Shurufa 在成功输入原文后短暂显示“整理失败，已输入原文”；无可用文本客户端且复制成功时显示“整理失败，已复制原文”。复制失败优先显示复制失败。只有本代次实际投递后才能保存提示，过期回调不能改变下一次录音。系统语音最终转写进入整理后，旧的识别/会话超时不再先行销毁原文；整理请求自己的 30 秒预算负责返回原文与失败状态。非 Shurufa 保留既有静默回退。

统一日志只记录 `voice_polish` 状态和耗时，不记录地址、模型、凭据或正文。未启用整理或没有凭据时不当作一次失败请求。

已启用且已有凭据时，系统语音与 TextStream/流式路径分别保存整理请求创建失败状态。超长提示词等配置被原生请求初始化拒绝后，仍在原文成功投递时显示同样短提示，不将 nil 请求误认为用户关闭了整理。明确的开关与旧字段冲突由[整理开关权威](2026-10-29-macos-polish-toggle-authority.md)修复。

### 既有笔记审计

[不完整整理回复](2026-10-19-voice-polish-incomplete-reply.md)部分重叠，继续定义失败条件；本篇改变 Shurufa 的失败展示。[持续录音](../feature/2026-10-28-shurufa-single-voice-session.md)继续持有代次和投递规则。[浮层预览](../feature/2026-10-29-shurufa-overlay-only-voice.md)继续规定实时文字位置。

## Alternatives considered

- 跟随 HTTP 重定向：可以兼容服务重写路径，但前缀到目录的跳转并不能确定对话资源，且改变既有凭据传输边界。
- 只手工修改本机地址：能修复当前配置，却保留模型列表能用、同一地址整理失败的入口差异。
- 继续静默回退：最少打断用户，但不能解释原文为何未整理，不符合用户批准的短提示方案。

## Consequences

支持明确的 API 前缀、完整标准对话路径和既有自定义路由，不修改已保存的地址。未知的非版本目录保持原样，用户可填写完整对话地址。UI 无弹窗，短提示复用浮层完成状态的 3 秒显示时长。自动化使用本机假服务核对前缀、完整路径、尾斜杠、查询参数、301 根目录场景、失败与超时标记；真实 AppKit 浮层导出明暗截图。此前真实合成请求的单次授权已用完，不为修复验收再次访问真实整理服务。服务端最终响应与实际录音体验仍待用户装机验收。
